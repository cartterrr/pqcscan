## Migration plan

### Fix now (classical problems) (immediately)

These are broken already, quantum computer or not: private keys in the repo, MD5/SHA-1, DES/RC4/ECB, TLS 1.0/1.1.

- **Private key embedded in file** (private key), 1 occurrence: `app/legacy_config.py:2`
- **MD5 / SHA-1 hash** (MD5/SHA-1), 3 occurrences: `app/crypto_utils.py:31`, `services/billing/src/main/java/Billing.java:25`, `web/src/session.ts:22`

- **Weak TLS cipher suites** (RC4/DES/3DES/NULL/EXPORT), 1 occurrence: `deploy/nginx.conf:5`

**What to do:**

- *Private key embedded in file:* A private key is checked into the repo. Rotate it, scrub it from git history, and load keys from a secret manager or HSM from now on.
- *MD5 / SHA-1 hash:* This is broken or deprecated even without a quantum computer, so fix it now: SHA-256 or better instead of MD5/SHA-1, AES-GCM or ChaCha20-Poly1305 instead of DES/3DES/RC4/ECB, and TLS 1.2 at minimum (1.3 if you can).

### Wave 1: key exchange and encryption (start now, done by 2030)

Data encrypted with RSA or ECDH today can be stored and decrypted later, so this goes first. The usual fix is hybrid ML-KEM.

- **RSA: key exchange / encryption** (RSA-OAEP), 4 occurrences: `app/crypto_utils.py:17`, `services/billing/src/main/java/Billing.java:12`, `services/gateway/main.go:24`, `web/src/session.ts:8`
- **RSA: key pairs (usage to confirm)** (RSA), 4 occurrences: `app/crypto_utils.py:11`, `services/billing/src/main/java/Billing.java:6`, `tests/test_crypto_utils.py:5 (test)`, `web/src/session.ts:4`
- **ECDH: key exchange / encryption** (ECDH/DH), 1 occurrence: `web/src/session.ts:12`
- **ECDHE: key exchange / encryption** (ECDHE), 1 occurrence: `services/gateway/main.go:15`
- **X25519: key exchange / encryption** (X25519), 1 occurrence: `app/crypto_utils.py:26`

**What to do:**

- *RSA: key exchange / encryption:* Anything encrypted this way can be recorded now and decrypted later, once a quantum computer exists. Switch key exchange to a hybrid of X25519 and ML-KEM-768 (FIPS 203). In TLS that means enabling the X25519MLKEM768 group, which OpenSSL 3.5+ and Go 1.24+ support. If the app wraps data keys with RSA-OAEP or ECDH itself, use a hybrid KEM there instead.
- *RSA: key pairs (usage to confirm):* It isn't clear from this line whether the key encrypts or signs. If it encrypts or does key exchange, treat it as urgent (hybrid ML-KEM); if it signs, it can wait for ML-DSA. Also note where the key is stored and how long the data it protects needs to stay secret.

### Wave 2: signatures and authentication (plan now, done by 2035)

To forge a signature you need the quantum computer at the time of the attack, so this can come after key exchange. Start with the long-lived stuff: root certificates, firmware and code signing.

- **RSA: signatures** (RSA-2048), 2 occurrences: `deploy/certs/api.crt`, `services/billing/src/main/java/Billing.java:18`
- **SSH keys: signatures** (ssh-rsa), 2 occurrences: `deploy/authorized_keys:1`, `deploy/authorized_keys:2`
- **ECDSA: signatures** (ECDSA), 2 occurrences: `app/crypto_utils.py:22`, `services/gateway/main.go:20`
- **RSASSA/ECDSA/Ed25519: signatures** (RSASSA/ECDSA/Ed25519), 2 occurrences: `web/src/session.ts:18`, `web/src/session.ts:19`
- **RS256/ES256/EdDSA: signatures** (RS256/ES256/EdDSA), 1 occurrence: `app/tokens.py:5`

**What to do:**

- *RSA: signatures:* A quantum computer could forge these signatures, but it can't go back and break old ones, so this can usually wait until key exchange is done. The replacement is ML-DSA-65 (FIPS 204), or SLH-DSA (FIPS 205) for long-lived roots and firmware signing. Reading the algorithm from config makes the switch much easier later.
- *RS256/ES256/EdDSA: signatures:* The JWT is signed with RSA, ECDSA or EdDSA. Tokens are short-lived, so this is not urgent, but whatever issues them should be able to change algorithm without a redeploy. IETF is working on ML-DSA for JOSE/COSE.
